| T34 | **The client shares the servers' network core.** `X2ServerProtocol`'s copies of the event/actor model (`Event`, `Performer`, `SimObject`, `ThreadManager`, `KncSend.h`...) and of the TCP `Socket/` are deleted; the client links `x2::common_net` (`src/server/Common/CommonNet.cmake`), which the servers' `Common` links too. `KSession` gets a **client side** (`KSession( bIsProxy, bClientSide )`): its own `KSADatabase` and the `*_Local` crypto calls, and `OnAuthenticFailed()` on every 10th failed packet, as the client copy did; only the client's proxies (`KActorProxy`, `KUserProxy`, `KTRUser`) and the `CX2ServerProtocol` facade stay in `src/client/X2ServerProtocol`. **One `MAX_PACKET_SIZE` of 64 KB**, the client's, for both sides (the original servers had 32 KB) | The copies were forks of `Common` that had drifted (logging, statistics, sequence numbers); one network layer keeps both ends of the protocol (T4) on the same framing and engine (T20), in the spirit of T33. 64 KB for both was chosen over one value per side so that one binary of the core serves both; the servers then accept any `USHORT` packet length and spend 64 KB more per connection. | T35 | **Client assets: one `.kom` library, tools on an extracted folder, loose files only in dev builds.** (1) `src/kom` (`x2::kom`, depends only on `x2::platform` and zlib) is the official implementation of the `.kom` format: reading (open, list from the XML header alone, thread-safe positional reads of entries, algorithms 0, 2 and 3; 1 kept opaque; sizes, times and checksums without decompressing), writing in separate headers (rewrite to a temporary file renamed over the original, untouched blobs copied verbatim, byte-identical when nothing changed) and mounting a folder of `.kom` (case-insensitive names; a name in more than one archive: the first in the client's load order wins, with a warning). `tools/kom/kom.py` stays as the test oracle until a C++ CLI replaces it. (2) **Tools never edit `.kom` directly**: they import the client's archives into an organized extracted folder (`client_data`, not versioned) plus a manifest that reproduces the original `.kom` byte for byte, and pack it back for distribution rebuilding only the archives that changed (new files go to archives chosen by a rule). Lua compile/decompile and `.kim` belong to the layer that manages that data, not to the `.kom` library. (3) **Install layout**: `/` launcher and its libraries; `/data` game root (`x2`, the `.kom`, game libraries); `/data/data` loose assets, only with `X2_DEV_TOOLS`. The release client reads only the `.kom` in `/data`; with `X2_DEV_TOOLS` it **prefers the loose files in `/data/data`**, falling back to the `.kom` | The original reads `.kom` in `KGCMassFileManager` with Win32 file handles and libxml2, rejects a whole archive when a name repeats, and in dev builds prefers the `.kom` over loose files; a portable library shared by the client, the launcher and the tools keeps one implementation of the format, and an extracted folder lets tools and people work on ordinary files without making patches large. See [`.kom` archives](../porting/kom.md). Chosen by the user (2026-11-05), from the agent's proposal |
| T36 | **Rendering goes through a graphics boundary, `x2::render` (`src/render`), with SDL_GPU as its only backend for now.** (1) `x2::render` is a thin API with the shape of modern graphics APIs, modeled on SDL_GPU: device, buffers, textures, samplers, shaders, explicit pipelines, command buffers, render and copy passes, bindings by slot, uniforms pushed by slot, texture readback. It exposes only what SDL_GPU does: nothing is added speculatively for a future backend; what one needs is added when it exists. (2) Fixed conventions at the boundary, the same as D3D: depth 0..1, texture origin at the top left; each backend adapts to them. (3) Backends are chosen at run time behind a `Device` interface, so a new one can sit beside SDL_GPU (selectable in config, compared in debug) instead of replacing it. `backends/sdlgpu` first; a null/recording backend for headless tests without a GPU. (4) **`SDL_gpu.h` appears only in `src/render/backends/sdlgpu`**, checked by a source-scan test, like `windows.h` in `src/platform`. `x2::app` keeps the window and events; `x2::render` creates the device from the window. Tools using ImGui's `sdlgpu3` backend reach the SDL_GPU device through an explicit escape hatch (`x2::render::sdlgpu::Native`) until an ImGui renderer on `x2::render` replaces it (x2 studio will need `x2::render` to draw game content anyway). (5) **The D3D9 translation lives above the boundary, once**, in `KTDXLIB`: D3D9 state cache → pipeline key → pipeline cache, fixed-function → shaders, the D3D9 half-pixel offset, effects (T37). Backends never see D3D9 concepts. Whether `KTDXLIB` emulates a subset of `IDirect3DDevice9` as a facade or its callers are rewritten to its own interface is decided in Phase 4 (**settled 2026-11-06 by T38**: its own interface) | SDL_GPU is already an abstraction over Vulkan, D3D12 and Metal, so a generic API on top of it would only add a layer; a boundary of the same shape keeps the SDL_GPU backend a near 1:1 wrapper (estimated at 1.5–2 thousand lines, 5–10% of Phase 4, 2026-11-06) while a Vulkan or D3D12 backend maps onto the same model. The expensive part (D3D9 emulation, `.x`, effects, DDS, fonts, the ~70 files that call the device) exists either way, and kept above the boundary it is written once. Chosen by the user (2026-11-06), from the agent's proposal; revises T19 and T32 |
| T37 | **The client's `.fx` effects are rewritten by hand as modern HLSL shaders versioned in `src/`** and compiled by SDL_shadercross (T19; offline, T39) into SPIR-V, DXIL and MSL with our own reflection data (samplers and uniforms per stage), which any future backend reuses. `KTDXLIB`'s effect class keeps the API its callers use (`SetTechnique`, `Begin`/`BeginPass`, `SetMatrix`... by parameter name), mapped to precompiled pipelines and uniform blocks. The `.fx` files in the `.kom` stay untouched and are not read (T1). The other assets are loaded as they are: `.dds` uploaded natively as BC1–3 (legacy formats converted to RGBA8 on load; software BC decoding only as a fallback for GPUs without it), `.tga` through stb_image, `.x` through our own parser (a derived cooked cache, keyed by the `.kom` checksum, only if load times call for it) | There are only 4 `.fx` (`XRenderer`, `RenderState`, `XPostEffect`, `GCSkin`, ~68 KB, 31 techniques; recounted 28 on 2026-11-07, of which only `XRenderer`'s 19 have a caller), almost all `vs_1_1` with fixed-function pixel stages (`ps_2_0` only in `XPostEffect`) ([Client dependencies](../original/client.md#d3dx-features-that-need-replacements), 2026-11-06). Emulating the D3DX effect framework (`.fx` parser, SM1 compiler, per-pass states) would cost more than porting 31 techniques, and the effects are code, not assets. Converting other assets offline gains nothing: `.x` would still need a parser in the converter, and BC textures are native everywhere on the desktop. T1 stands. Chosen by the user (2026-11-06), from the agent's proposal |
| T38 | **`KTDXLIB` exposes its own device interface, not an `IDirect3DDevice9` facade** (settles T36 (5)). A `KTDXLIB` device class owns the D3D9 translation on `x2::render` (state cache → pipeline key → pipeline cache, fixed-function → shaders, the half-pixel offset, dynamic vertex data on transfer buffers) with D3D9-like methods (D3D9's type names, `LPDIRECT3DDEVICE9`, `LPDIRECT3DTEXTURE9`..., alias its classes) but no COM: no `AddRef`/`Release`, `HRESULT`, surfaces as objects, `Reset` or lost devices. The `KTDXLIB` files that call the device are rewritten onto it, and `X2Lib`'s loading-screen `BeginScene`/`EndScene`/`Present` triplets become one engine call. **The D3D9 vocabulary stays**: `D3DRS_*`, `D3DTSS_*`, `D3DSAMP_*`, `D3DFVF_*`, `D3DPT_*`, `D3DFMT_*`, `D3DBLEND_*`... with the same names and values, in a `KTDXLIB` header, so the callers of `CKTDGStateManager` and `CKTDGDynamicVBManager` keep compiling unchanged | Survey (comments excluded, 2026-11-06): 29 files call the device directly, 17 in `KTDXLIB`, 11 in `X2Lib` (32 of whose calls are the loading-screen triplets) and 1 in `X2`; render states already go through `CKTDGStateManager` (23 `KTDXLIB` and 12 `X2Lib` files) and draws through `CKTDGDynamicVBManager`. About 55 device methods are used, a small subset (strips, fans, lists, lines, points; mostly `XYZRHW\|DIFFUSE\|TEX1` and `XYZ\|DIFFUSE\|TEX1`; texture ops `DISABLE`, `MODULATE`, `ADD`, `SELECTARG1/2`, `ADDSIGNED`). A facade would carry COM and lost-device semantics nobody needs and pull `ID3DXMesh` and the animation controller toward the same emulation. Chosen by the user (2026-11-06), from the agent's proposal |

| T41 | **The client simulates at fixed ticks and renders at any rate, interpolating between ticks.** `CKTDXApp::OnFrameMove` keeps the original's fixed steps (`m_fConstElapsedTime`, set per state by `SetFrameRate`: 85, 75, 60 in the village, 70 in dungeons...), so the simulation, the frame-counted P2P sync and NPC timing are unchanged; it no longer sleeps to the next step, and every loop renders. Rendering shows the state between the last two ticks: the camera, and skinned meshes (root and bones), are interpolated by the fraction of a tick elapsed, only in what is drawn (the simulation never reads the interpolated values), snapping when an object or the camera jumps. Vsync presents FIFO at the monitor's rate; with vsync off, an optional frame limit (`GameOptions.lua`).
