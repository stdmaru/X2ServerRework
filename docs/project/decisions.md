# Decisões

## Tomadas

| # | Decisão | Motivo |
|---|---|---|
| T1 | Assets do cliente não mudam; o código se adapta aos formatos atuais | Pedido do projeto |
| T2 | Ferramentas (`X2Tool`, patcher, `*DBManager`...) ficam fora do porte inicial | Foco em servidor + cliente + libs |
| T3 | Bibliotecas de terceiros entram pela versão **upstream**, não a cópia do `_reference` | As cópias são antigas, modificadas e só-Windows |
| T4 | Compatibilidade de rede com o `x2.exe`/`elsword.exe` original (antiga D1) | Validar o servidor sem ter o cliente portado |
| T5 | Variante **US / `_SERVICE_`** (antiga D2) | Config já usada no porte VS2026 do `_reference` |
| T6 | Alvo **64 bits** (antiga D5) | — |
| T7 | Manter **MSSQL via ODBC** por enquanto (antiga D6) | Migrar SGBD é projeto à parte |
| T8 | Ordem: **bibliotecas → servidor → cliente** | Servidor é menor e testável com o cliente original |
| T9 | `_reference` fica **intocado**; código novo do zero em `src/`, alimentado por um **importador automático** (seleção por vcxproj + CP949→UTF-8 + resolução de `#if` + exclusões) | Limpar o original exigiria compilar no Windows/MSVC x86 a cada passo; copiar à mão 2 M linhas é inviável e perderia a limpeza das flags |
| T10 | Base `_SERVICE_`, **mantendo ferramentas de debug/dev/admin** sob uma flag nova `X2_DEV_TOOLS` (build `Development`). Descartar o resto: flags não usadas, legado, outros países, anti-cheat | `_IN_HOUSE_` mistura debug com gameplay não lançado; whitelist + relatório em [Debug e dev](../original/debug-and-development.md) |
| T11 | **Camada de compatibilidade** `x2::platform`: os nomes Win32/ATL usados em massa (`CTime`, `DWORD`, `CString`, `CRITICAL_SECTION`, eventos, `GetTickCount`...) são oferecidos com a mesma semântica; no Windows vêm do `windows.h` real. Modernização para `std::` só na Fase 5 | `CTime` aparece ~1.700×, `DWORD` ~900× e macros de log ~13.500× no servidor; reescrever durante o porte multiplicaria o risco. Ver [Plataforma](../porting/platform.md) |
| T12 | **arm64** é alvo futuro: nada de asm/intrínsecos x86 no código novo, `char` com sinal (`-fsigned-char`), dependências que suportam arm64 | Pedido do projeto (2026-10-29) |
| T13 | Dependências: `find_package` primeiro, `FetchContent` com versão e hash fixos como reserva (antiga D3). doctest só como header (o Crypto++ saiu na T27) | Funciona igual em Linux e Windows sem gerenciador de pacotes obrigatório |
| T14 | Layout: `src/platform`, `src/kncsdk`, depois `src/server/...` e `src/client/...`; cada módulo importado espelha a estrutura original até a Fase 5 | Não precisa reescrever includes na importação |
| T15 | **UI do servidor = terminal em todas as plataformas** (o MFC sai, inclusive no Windows). O terminal reproduz a janela original: log ao vivo, prompt que executa **Lua** (como o campo de entrada do `CServerUIDlg`) com histórico, status `_Loading`/`_Ready` no título do terminal, confirmação ao encerrar e modo sem stdin para rodar como serviço. ~~Um `--gui` portável (ImGui + SDL3, igual nas duas plataformas) fica como front-end opcional futuro, sobre a mesma API de comandos/log~~. **Revisada em 2026-10-31**: o servidor não terá interface gráfica nenhuma, nem `--gui`; a janela vira a ferramenta à parte da T30 | Um caminho de código só; o MFC não é portável. Decisão delegada ao agente pelo usuário (2026-10-29); revisão escolhida pelo usuário (2026-10-31) |
| T16 | **Log**: o arquivo mantém o conteúdo completo do original (nível, função, data, dados, `BUILD_LOG`, arquivo/linha). O console tem renderização própria, compacta e colorida (`HH:MM:SS NÍVEL Função: mensagem`, campos `BUILD_LOG` alinhados abaixo), com nível de filtro independente do arquivo. `START_LOG` passa a entregar metadados estruturados ao logger em vez de texto pronto | O conteúdo do original é útil para diagnóstico, mas confuso no console. Decisão delegada ao agente pelo usuário (2026-10-29) |
| T17 | **MSSQL via API ODBC**, driver **Microsoft ODBC Driver 18** (Windows e Linux, x64/arm64) e FreeTDS como alternativa sem mudar código. Os `.dsn` viram *connection strings* na configuração. No unixODBC, `SQLWCHAR` é UTF-16: a camada ODBC converte de/para `wchar_t` | O wrapper original (`KODBC`/`StoredProcedure`) é ODBC; o driver oficial é o mais completo (TLS, tipos, desempenho). Detalha a T7. Delegado ao agente pelo usuário (2026-10-29) |
| T18 | ~~MinGW-w64 cruzado a partir do Linux, com testes no Wine, como verificação contínua dos caminhos `_WIN32`~~. **Substituída pela T26 (2026-10-30)**: com um Windows de verdade no CI, o MinGW (outro ABI e outro CRT) deixou de compensar. Valeu de 2026-10-29 a 2026-10-30 e achou bugs reais (`printf` ISO do MinGW, `UNICODE` não definido) | Na época não havia máquina Windows; sem isso o código Windows só seria compilado na hora de validar no MSVC, acumulando erros. Delegado ao agente pelo usuário (2026-10-29) |
| T19 | **SDL3** para janela/input/áudio e **SDL_GPU** para render no cliente (antiga D4), com shaders via SDL_shadercross. Vulkan direto e ponte DXVK descartados como alvo | Vulkan/D3D12/Metal de graça com muito menos código; o D3D9 está concentrado no `KTDXLIB`. Escolhido pelo usuário com a recomendação do agente (2026-10-29) |
| T20 | **Rede do servidor sobre Asio standalone** (1.30.2, FetchContent), escondido em `x2::platform` (`net_io.h`: `IoService`, `TcpStream`); o Asio não aparece em headers fora de `src/platform`. A API do original (`KIocp`, `KSocketObject`, `KSession`, chaves de completion, modo sem IOCP com eventos) é mantida, só o motor muda. UDP (`KTDNUDP`) sai em passo próprio | Asio é proactor como o IOCP (usa IOCP no Windows e epoll no Linux), então o modelo do original encaixa sem reescrever as sessões; header-only, x64/arm64. Delegado ao agente pelo usuário (2026-10-29) |
| T21 | **LuaJIT 2.1 upstream, sem as modificações da KOG**, no servidor e no cliente, num commit fixo (o mesmo do pacote do sistema). Linux: pkg-config primeiro (a imagem Ubuntu da T24 não instala o pacote, que lá é o fork OpenResty); MinGW (e Linux sem o pacote): fonte baixada com hash fixo e compilada pelo Makefile do LuaJIT, chamado pelo CMake. As mudanças da cópia 2.0.2 do cliente (cabeçalho de bytecode `\x1bKL\x81`, codificação/BOM, parser removido) não são levadas; os scripts do cliente serão recompilados ou carregados como fonte quando o cliente for portado ([Bibliotecas](../original/libraries.md#luajit-da-kog)). Resolve a parte MinGW da D5 | 2.0.2 não roda em arm64 (T12) e em x64 limita os objetos Lua à memória baixa (sem GC64); mesma versão em todas as plataformas. Escolhido pelo usuário, que aceita recompilar os scripts (2026-10-30) |
| T22 | **Pastas prontas para rodar, sem depender do `_reference`** (que será apagado no fim do projeto). Tudo o que os servidores leem fica versionado em `runtime/`, menos binários e assets do cliente: `ServerResource/` (os scripts do servidor em produção, `_original-server`, com os bytes intactos), configs e `.dsn` como templates `*.in` (sem senha). O `ClientScript` que os servidores leem é **gerado dos `.kom` do cliente** (`tools/runtime/gen_clientscript.py`, sobre `tools/kom`). Os alvos `x2_run_<servidor>` montam `build/<preset>/run/` com o mesmo layout do original. Os dados do banco de desenvolvimento podem mudar (por script); a estrutura não | Rodar com um comando, igual em toda máquina, e o repositório se basta sem o `_reference`. O `ClientScript` do servidor original é de outra versão do cliente (2016–2019) e de outro formato; gerado do cliente, fica coerente com o `elsword.exe` em uso. Escolhido pelo usuário com o agente (2026-10-30) |
| T23 | **EPublisherServer**: o `AuthServer` (DEB, do dono do projeto) é **reimplementado** em `src/server/EPublisherServer`, com o nome que o código original dá a esse serviço (`EPUBLISHER_*`, login e compras). Mesmo protocolo (SOAP/HTTP do cliente gSOAP dos servidores), mesmas tabelas (`DEBAccounts`, `DEBUserCash`), sobre o `KODBC`, sem SOCI/OpenSSL/gSOAP no servidor. Conta como código original até a Fase 5, quando a função deve ir para o ChannelServer. Ele pode usar o `Common`; **nada do `Common` ou dos outros servidores usa ele** | Evita dependências novas e usa o mesmo acesso a banco dos servidores. Liberdade total dada pelo usuário, com a regra de separação e o nome (2026-10-30) |
| T24 | **Builds e testes numa imagem Docker Ubuntu LTS** (`docker/build/Dockerfile`, `ubuntu:26.04`), a mesma no desenvolvimento (`docker/build.sh`) e no CI (publicada no GHCR pelo hash do `Dockerfile`). O host só precisa de Docker. GCC, Clang e CMake são os do Ubuntu, não os mais novos; o Windows fica fora da imagem (T26); o código continua sem warnings em ambos ([Ambiente de build](../tools/build-environment.md)) | Ubuntu é o padrão mais usado e o preferido do GitHub; um ambiente único e reproduzível em todas as máquinas e no CI. Pedido do usuário (2026-10-30) |
| T25 | **LuaJIT no MSVC pelo `msvcbuild.bat`** do próprio LuaJIT (antiga D5), chamado pela mesma receita do CMake da T21 (`static`, CRT dos nossos alvos via `CL`). O LuaJIT é C compilado pelo `cl` do Visual Studio, ABI compatível com o clang-cl da T26. Validado pelo job **clang-cl Debug** do CI em `windows-latest` | Mesmo commit fixo e mesmo caminho do MinGW, sem vcpkg nem binário de terceiros. Escolhido pelo usuário (2026-10-30), com o CI do GitHub dando a máquina Windows que faltava |
| T26 | **Um compilador de Windows, clang-cl; Clang como compilador do Linux; GCC só como verificação.** Windows: clang-cl (front-end do Clang com os cabeçalhos, a STL, o SDK e o linker do Visual Studio, ABI do MSVC), compilado e testado no CI num runner `windows-latest`, preset `windows-*`; é o build distribuído. Linux: os presets `linux-*` usam Clang (build distribuído); o preset `linux-gcc` (Release) só verifica, no CI e quando preciso. Saem o `cl` e o MinGW + Wine (T18). Zero warnings em GCC, Clang e clang-cl | O clang-cl tem os mesmos diagnósticos do Clang: o trabalho de manter o código limpo cai para duas famílias (GCC e Clang), não quatro. O MinGW era aproximação sem Windows; o CI agora dá um Windows real com o toolset distribuído. O GCC é o padrão do Ubuntu e acha coisas que o Clang não acha. Testar Windows localmente deixa de ser possível (ciclo pelo CI); o clang-cl cruzado do Linux pode ser montado depois. Recomendação aceita pelo usuário (2026-10-30) |
| T27 | **Sem Crypto++: cripto própria em `src/kncsdk/Crypto` (`x2::crypto`)**, só o que o protocolo e os bancos do original pedem: DES-CBC sem padding, HMAC-MD5 (ICV truncado do `KncSecurity`), MD5 (`KncUtil::GetMD5`), SHA-256 (senhas do EPublisherServer) e hex. Escrita a partir das especificações (FIPS 46-3, RFC 1321, FIPS 180-4, RFC 2104), conferida com os vetores oficiais e, antes de remover o Crypto++, idêntica a ele em 5.000 entradas aleatórias. O gerador aleatório do Crypto++ não era usado e saiu sem substituto | O Crypto++ 8.9 não compila com clang-cl (trava incondicional para `_MSC_VER` + `__clang__`) nem com a STL do VS 2026 (iteradores `stdext` removidos, alocador incompatível), e o upstream anda devagar. DES e MD5 estão aqui só por compatibilidade com o cliente, sem segurança a proteger. Some uma dependência inteira (~150 arquivos compilados), também para arm64. Escolhido pelo usuário (2026-10-30) |
| T28 | **Os `.lua` da pasta de cada servidor de produção vão para o `runtime/ServerResource`, no lugar das versões de lá**; nenhum `.lua` de dados fica em `runtime/<Servidor>/`. Os que não são carregados por nada ficam de fora ([Pastas de execução](../tools/runtime.md#scripts-da-pasta-de-cada-servidor-2026-10-31-t28)) | Em produção a pasta do servidor tinha prioridade na busca (`KAutoPath`): é o que o jogo rodava. Um lugar só para os scripts, como os servidores já procuram. Escolhido pelo usuário (2026-10-31), contra mesclar entrada a entrada |
| T29 | **Ferramentas gráficas do projeto em SDL3 + ImGui**, sobre o código SDL3 do cliente (T19). A divisão fica: **servidores** só em terminal (stdout/stdin, T15), **cliente** em SDL3 + SDL_GPU (T19), **ferramentas** (a suíte de desenvolvimento do cliente: mapas, UI, fases, `.kom`; e o ServerManager da T30) em SDL3 + ImGui | Um toolkit só para as ferramentas, que reaproveita a janela, o input e o backend do cliente em vez de trazer outro (Qt). Escolhido pelo usuário (2026-10-31). Não contradiz a T2: são ferramentas novas, não o porte das originais |
| T30 | **ServerManager: ferramenta standalone que orquestra e monitora os servidores**, separada da suíte do cliente. Abre os servidores na ordem certa, mostra o log de cada um (filtro, busca), dá um prompt Lua por servidor e o status. Funciona **local** (processos filhos, por pipe) e **remoto por SSH** (`ssh host ...`), para um desktop controlar uma máquina Linux só de terminal. O servidor não ganha nada gráfico nem porta nova: só um modo de saída para máquina (log estruturado da T16 em linhas, comandos pelo stdin) e, para se ligar a um servidor que já roda como serviço, um socket local (Unix socket / *named pipe*) com um utilitário que o liga ao stdin/stdout (`x2ctl attach`). Formato e nomes se definem na implementação | O console executa Lua no processo do jogo: autenticação e criptografia ficam com o SSH, sem código de rede de admin no servidor. Uma janela para todos os servidores, em qualquer máquina, no lugar das janelas MFC (que também eram só locais). Escolhido pelo usuário (2026-10-31) |
| T31 | **Sem gSOAP: o cliente DEB dos servidores (`KDEBAuth`, `KDEBBilling`) fala SOAP/HTTP por código próprio** (`Common/OnlyGlobal/AuthAndBilling/DEB`: mensagens SOAP e um cliente HTTP/1.1 bloqueante), o mesmo código de mensagens que o EPublisherServer usa do lado servidor. O login e o billing do DEB continuam iguais: mesmas operações (`Login`, `GetUserCash`, `PurchaseProduct`), mesmo envelope e cabeçalhos que o gSOAP 2.7 escrevia, então um AuthServer externo continua servindo. Saem o runtime do gSOAP (`stdsoap2`) e o código que ele gerou | O gSOAP era a última dependência de terceiros copiada do `_reference` nos servidores (17 mil linhas compiladas sem warnings), e o EPublisherServer já tinha a metade servidora. Corrige de passagem a dupla codificação de texto não ASCII do gSOAP. Escolhido pelo usuário (2026-10-31), que pediu manter a autenticação e o billing do DEB |
