# Decisions

## Accepted

| # | Decision | Rationale |
|---|---|---|
| T1 | Client assets do not change; the code adapts to their current formats | Project request |
| T2 | Original tools (`X2Tool`, patcher, `*DBManager`, ...) are outside the initial port | Focus on the server, client, and libraries |
| T3 | Use upstream third-party libraries, not the copies in `_reference` | The copies are old, modified, and Windows-only |
| T4 | Preserve network compatibility with the original `x2.exe` / `elsword.exe` (formerly D1) | Validate the server before the client is ported |
| T5 | Use the **US / `_SERVICE_`** variant (formerly D2) | This is the configuration already used for the VS2026 port of `_reference` |
| T6 | **64-bit** targets only (formerly D5) | — |
| T7 | Keep **MSSQL over ODBC** for now (formerly D6) | Database migration is a separate project |
| T8 | Order: **libraries → server → client** | The server is smaller and can be tested with the original client |
| T9 | Keep `_reference` **untouched**; create new code in `src/` using an **automatic importer** (vcxproj selection + CP949→UTF-8 + `#if` resolution + exclusions) | Cleaning the original would require compiling with Windows/MSVC x86 at every step; manually copying 2 million lines is impractical and would lose flag cleanup |
| T10 | Base the port on `_SERVICE_`, **retaining debug/dev/admin tools** behind a new `X2_DEV_TOOLS` flag (`Development` build). Discard unused flags, legacy code, other countries, and anti-cheat | `_IN_HOUSE_` mixes debugging with unreleased gameplay changes; use a whitelist and report ([Debug and development](../original/debug-and-development.md)) |
| T11 | **Compatibility layer** `x2::platform`: provide the widely used Win32/ATL names (`CTime`, `DWORD`, `CString`, `CRITICAL_SECTION`, events, `GetTickCount`, ...) with matching semantics; use real `windows.h` on Windows. Modernize to `std::` only in Phase 5 | `CTime` appears ~1,700 times, `DWORD` ~900 times, and logging macros ~13,500 times in the server; rewriting during the port would multiply risk. See [Platform](../porting/platform.md) |
| T12 | **Linux arm64 is a supported target**, alongside x86_64 (Windows remains x86_64): no x86 assembly/intrinsics in new code, signed `char` (`-fsigned-char`), and arm64-compatible dependencies. **Revised 2026-11-01**: the ARM64 build and test suite pass, and LoginServer authentication has been verified | Project request (2026-10-29) |
| T13 | Dependencies: try `find_package` first, then pinned `FetchContent` versions and hashes as a fallback (formerly D3). doctest is header-only (Crypto++ was removed in T27) | Works on Linux and Windows without requiring a package manager |
| T14 | Layout: `src/platform`, `src/kncsdk`, then `src/server/...` and `src/client/...`; each imported module mirrors the original structure until Phase 5 | Avoids rewriting includes during import |
| T15 | **Server UI is terminal-based on every platform** (MFC is removed, including on Windows). The terminal preserves key features of the original window: live logs, a Lua prompt (`CServerUIDlg` input field) with history, `_Loading`/`_Ready` status in the terminal title, shutdown confirmation, and a no-stdin service mode. ~~A portable `--gui` (ImGui + SDL3 on both platforms) could be an optional future front-end over the same command/log API.~~ **Revised 2026-10-31**: servers will have no GUI, including no `--gui`; the window becomes a separate tool under T30 | One code path; MFC is not portable. Delegated to the agent by the user (2026-10-29); revision chosen by the user (2026-10-31) |
| T16 | **Logging**: log files retain the original's full content (level, function, date, data, `BUILD_LOG`, file/line). The console gets its own compact, colored rendering (`HH:MM:SS LEVEL Function: message`, with aligned `BUILD_LOG` fields below) and an independent filter level. `START_LOG` passes structured metadata to the logger instead of preformatted text | The original log is useful for diagnosis but confusing in the console. Delegated to the agent by the user (2026-10-29) |
| T17 | **MSSQL through the ODBC API**, using **Microsoft ODBC Driver 18** (Windows and Linux, x64/arm64), with FreeTDS as a drop-in alternative. `.dsn` files become connection strings in configuration. With unixODBC, `SQLWCHAR` is UTF-16; the ODBC layer converts to/from `wchar_t` | The original `KODBC`/`StoredProcedure` wrapper uses ODBC; the official driver is the most complete (TLS, types, performance). Expands on T7. Delegated by the user (2026-10-29) |
| T18 | ~~Cross-compile with MinGW-w64 from Linux and test with Wine as continuous validation of `_WIN32` paths~~. **Superseded by T26 (2026-10-30)**: with a real Windows machine in CI, MinGW (a different ABI and CRT) was no longer worth maintaining. It was used from 2026-10-29 to 2026-10-30 and found real bugs (MinGW ISO `printf`, `UNICODE` undefined) | At the time there was no Windows machine; Windows code would only be compiled during MSVC validation, accumulating errors. Delegated to the agent by the user (2026-10-29) |
| T19 | **SDL3** for client window/input/audio and **SDL_GPU** for rendering (formerly D4), with shaders via SDL_shadercross. Direct Vulkan and a DXVK bridge are not targets | Vulkan/D3D12/Metal for free, with much less code; D3D9 is concentrated in `KTDXLIB`. Chosen by the user following the agent's recommendation (2026-10-29) |
| T20 | **Server networking uses standalone Asio** (1.30.2, FetchContent), hidden behind `x2::platform` (`net_io.h`: `IoService`, `TcpStream`); Asio does not appear in headers outside `src/platform`. Preserve the original API (`KIocp`, `KSocketObject`, `KSession`, completion keys, event-based mode without IOCP); only the engine changes. UDP (`KTDNUDP`) is a separate step | Asio's proactor model maps well to IOCP (it uses IOCP on Windows and epoll on Linux), so the original session model can be retained without rewriting sessions. Asio is header-only and supports x64/arm64. Delegated to the agent by the user (2026-10-29) |
| T21 | **Upstream LuaJIT 2.1, without KOG modifications**, for server and client, pinned to a commit (same version as the system package). Linux tries pkg-config first (Ubuntu T24 image does not install its LuaJIT package because that package is the OpenResty fork); MinGW (and Linux without package) fetches pinned source hash and builds with LuaJIT's Makefile invoked by CMake. Do not carry over client's 2.0.2 changes (bytecode header `\x1bKL\x81`, encoding/BOM, removed parser); recompile client scripts or load source when porting client ([Libraries](../original/libraries.md#kogs-luajit)). Resolves MinGW part of D5 | 2.0.2 does not run on arm64 (T12) and limits Lua objects to low memory on x64 (no GC64); use one version on all platforms. Chosen by the user, who accepts recompiling scripts (2026-10-30) |
| T22 | **Server package under repository-root `dist/`, without `_reference`** (which will be deleted at project end). Version everything the servers need at runtime under `runtime/`, except binaries and client assets: `ServerResource/` (production server scripts, byte-for-byte from `_original-server`), configs, and `*.in` `.dsn` templates (no passwords). Generate the servers' `ClientScript` from the client's `.kom` files (`tools/runtime/gen_clientscript.py`, using `tools/kom`). `x2_run_<server>` targets assemble the package with the original layout. All presets share `dist/`. Development database data may change (via scripts), but its structure may not | One command to run on any machine, and the repository is self-contained without `_reference`. The original server's `ClientScript` is from a different client version (2016–2019) and format; generating it from the client keeps it consistent with the active `elsword.exe`. Initially chosen 2026-10-30; destination changed at the user's request on 2026-11-03 |
| T23 | **EPublisherServer**: reimplement the project owner's DEB `AuthServer` in `src/server/EPublisherServer`, using the service name from the original (`EPUBLISHER_*`, login and purchases). Keep the same protocol (SOAP/HTTP from the servers' gSOAP client), tables (`DEBAccounts`, `DEBUserCash`), and `KODBC`; do not add SOCI/OpenSSL/gSOAP to the server. Treat it as original code until Phase 5, when the functionality should move into ChannelServer. It may use `Common`; **neither `Common` nor other servers may depend on it** | Avoids new dependencies and uses the servers' existing database access. The user granted full implementation freedom, subject to separation and naming (2026-10-30) |
| T24 | **Build and test in a Docker Ubuntu LTS image** (`docker/build/Dockerfile`, `ubuntu:26.04`), shared by development (`docker/build.sh`) and CI (published to GHCR using the Dockerfile hash). The host only needs Docker. Use Ubuntu's GCC, Clang, and CMake rather than the newest releases; Windows is outside the image (T26); both builds remain warning-free ([Build environment](../tools/build-environment.md)) | Ubuntu is widely used and preferred by GitHub; one reproducible environment across developer machines and CI. User request (2026-10-30) |
| T25 | **Build LuaJIT with MSVC using its own `msvcbuild.bat`** (formerly D5), via the same CMake recipe as T21 (`static`, using target CRT through `CL`). LuaJIT is C compiled by Visual Studio's `cl`, ABI-compatible with T26 clang-cl. Validated by CI **clang-cl Debug** job on `windows-latest` | Same pinned commit and approach as MinGW, without vcpkg or third-party binaries. Chosen by the user (2026-10-30), with GitHub CI providing the missing Windows machine |
| T26 | **Use clang-cl on Windows, Clang on Linux, and GCC only for checks.** Windows: clang-cl (Clang front-end with Visual Studio headers, STL, SDK, and linker; MSVC ABI), built and tested in CI on `windows-latest` with `windows-*` presets; this is the distributed build. Linux: `linux-*` presets use Clang (distributed build); `linux-gcc` Release is only a check, in CI and when needed. Remove `cl` and MinGW + Wine (T18). Zero warnings with GCC, Clang, and clang-cl | clang-cl has Clang's diagnostics, reducing code-cleanliness work to two compiler families (GCC and Clang), not four. MinGW was an approximation without Windows; CI now provides real Windows with the distribution toolchain. GCC is Ubuntu's default and finds issues Clang misses. Local Windows testing becomes a CI cycle; a Linux-hosted clang-cl cross-build can be added later. User accepted the recommendation (2026-10-30) |
| T27 | **No Crypto++: implement only the cryptography required by the original protocol and databases** in `src/kncsdk/Crypto` (`x2::crypto`): DES-CBC without padding, HMAC-MD5 (the truncated `KncSecurity` ICV), MD5 (`KncUtil::GetMD5`), SHA-256 (EPublisherServer passwords), and hex. Implemented from specifications (FIPS 46-3, RFC 1321, FIPS 180-4, RFC 2104), checked against official vectors and, before removing Crypto++, matched it for 5,000 random inputs. Crypto++'s random generator was unused and removed without replacement | Crypto++ 8.9 does not compile with clang-cl (unconditional stop for `_MSC_VER` + `__clang__`) or the VS 2026 STL (removed `stdext` iterators, incompatible allocator), and upstream development is slow. DES and MD5 remain only for client compatibility, not security. Removes an entire dependency (~150 compiled files), including for arm64. Chosen by the user (2026-10-30) |
| T28 | **Place each production server's `.lua` files in `runtime/ServerResource`, replacing the versions there**; do not keep data `.lua` files under `runtime/<Server>/`. Exclude files that nothing loads ([Server package](../tools/runtime.md#scripts-from-each-server-folder-2026-10-31-t28)) | In production, the server folder had priority in the search (`KAutoPath`): those were the scripts the game ran. Keep scripts in one place, matching how servers already search. Chosen by the user (2026-10-31), rejecting entry-by-entry merging |
| T29 | **Project GUI tools use SDL3 + ImGui**, built on the client's SDL3 code (T19). Split responsibilities: **servers** use terminal only (stdout/stdin, T15), the **client** uses SDL3 + SDL_GPU (T19), and **tools** (client development suite: maps, UI, stages, `.kom`; plus ServerManager from T30) use SDL3 + ImGui | One toolkit for tools that reuses the client's window, input, and backend instead of adding another (Qt). Chosen by the user (2026-10-31). Does not conflict with T2: these are new tools, not ports of the originals |
| T30 | **ServerManager is a standalone tool to orchestrate and monitor servers**, separate from the client suite. It starts servers in the right order, shows each server's logs (filter/search), provides a Lua prompt per server, and shows status. It works **locally** (child processes over pipes) and **remotely over SSH** (`ssh host ...`), so a desktop can manage a terminal-only Linux machine. Servers get no GUI or new port: only machine-readable output (T16 structured logs as lines, commands through stdin) and, to connect to a server already running as a service, a local socket (Unix socket / *named pipe*) plus a utility that bridges it to stdin/stdout (`x2ctl attach`). Define format and names during implementation | The console executes Lua in the game process: authentication and encryption remain with SSH, with no admin networking code in the server. One window for all servers on any machine, instead of the MFC windows (which were local-only). Chosen by the user (2026-10-31) |
| T31 | **Remove gSOAP: the servers' DEB client (`KDEBAuth`, `KDEBBilling`) uses a custom SOAP/HTTP implementation** (`Common/OnlyGlobal/AuthAndBilling/DEB`: SOAP messages and a blocking HTTP/1.1 client), sharing message code with EPublisherServer. DEB login and billing remain unchanged: same operations (`Login`, `GetUserCash`, `PurchaseProduct`), same envelope and headers written by gSOAP 2.7, so an external AuthServer still works. Remove the gSOAP runtime (`stdsoap2`) and generated code | gSOAP was the last copied third-party server dependency from `_reference` (17,000 compiled lines without warnings), and EPublisherServer already had the server-side half. Also fixes gSOAP's double-encoding of non-ASCII text. Chosen by the user (2026-10-31), who requested that DEB authentication and billing remain |
| T32 | **The shared SDL3 + ImGui foundation lives in `src/app`**, built by ServerManager first and reused by the client in Phase 3: `x2::app` (SDL3 window, events, SDL_GPU device; no ImGui) for the client and tools, and `x2::app_imgui` (ImGui with the `sdl3` and `sdlgpu3` backends) for tools only. Tools live under `src/tools/<Tool>`. Process spawning with pipes belongs to `x2::platform` (`process.h`). SDL3: pinned `FetchContent`, **always built from source and linked statically** on Linux and Windows, an exception to T13's `find_package` first (**revised 2026-11-04**: it first used Ubuntu's `libsdl3-dev` copied next to the executable). ImGui: pinned `FetchContent` only (packages do not reliably ship the `sdlgpu3` backend) | ServerManager is built before the client (the roadmap had it after the client's SDL3 code, T29), so the base has the client's shape: SDL_GPU (T19), not SDL_Renderer or OpenGL. Servers never link SDL. GUI is tested on the user's desktop, not in the container. A static SDL makes one self-contained executable with the same SDL everywhere; SDL still loads X11/Wayland/audio libraries at run time. Chosen by the user (2026-11-04) |
| T33 | **Client and server share one `Common`.** The client does not import its own copy of the server's `Common` files: it compiles the ones in `src/server/Common` (packets, event IDs, enums, `KncUidType.h`, `NetError`), as the original client included `../KncWX2Server/Common`. They are resolved once, with the server set, and stay where T14 puts them until Phase 5; the same holds the other way for `X2Lib/X2UDPPacket.*`, which the servers already compile from `src/server/X2Lib`. Where the client needs something different, adapt the shared file in `src/` instead of forking it. Client-only code is resolved with `client.generated.toml` | One packet definition for both ends of the protocol (T4). `compare_flags.py` found two conflicts in the 48 shared files, neither a layout difference on the wire (`ADD_RENA_SYSTEM` is undefined on both sides; `X2OPTIMIZE_NPC_NONHOST_SIMULATION` changes UDP NPC-sync structs that the servers never use, and becomes true, the client's value) and no differing value among the 1,188 flags both sets know ([Flags](../tools/flags.md#server-and-client-in-shared-code-2026-11-05)). Chosen by the user (2026-11-05) |
